UNIDAD 1: Arquitectura y protocolos web avanzados

Temas del programa: Modelo cliente–servidor revisitado. Capas y responsabilidades. HTTP/1.1 vs HTTP/2 vs HTTP/3 (h/2, QUIC). CORS, políticas de caché, CDN y compresión.

Apuntes existentes:

  • redes.md — modelo TCP/IP, capas de acceso/internet/transporte/aplicación, NAT y resolución de nombres, herramientas de diagnóstico, redes con Docker, sockets en Python (2026 líneas, 16 secciones)
  • deployment_apunte.md — NGINX como proxy reverso, SSL/TLS, certificados (cubre la parte de infraestructura del modelo cliente–servidor)

Estado: 🟡 Parcial. Las capas y el modelo cliente–servidor están bien servidos por redes.md , pero desde la óptica de redes, no de HTTP aplicado.

Falta escribir:

  • Comparativa HTTP/1.1 vs HTTP/2 vs HTTP/3: multiplexing, head-of-line blocking, server push, QUIC sobre UDP
  • Políticas de caché HTTP ( Cache-Control , ETag , revalidación)
  • CDN: qué resuelve, cuándo conviene
  • Compresión (gzip / brotli) y negociación de contenido
  • CORS como protocolo (el preflight está parcialmente en la Unidad 7, ver más abajo)

UNIDAD 2: Diseño y documentación de APIs

Temas del programa: REST (recursos, verbos, códigos), HATEOAS. GraphQL (tipos, queries, mutations). Especificación y documentación con OpenAPI/Swagger. Versionado, compatibilidad y deprecaciones. Paginación, ordenamientos y filtros; convenciones.

Apuntes de la unidad (nuevos, en notes/Prog4/New/ ):

  1. u02_rest_diseno.md — Diseño de APIs REST : recursos vs acciones, diseño de URIs, métodos seguros e idempotentes, PUT vs PATCH, códigos de estado, errores uniformes con problem+json (RFC 9457) y middleware centralizado, colecciones (paginación offset vs cursor, orden, filtros validados con Zod, sobre { data, meta, links } ), versionado y deprecación ( Deprecation / Sunset ), HATEOAS y modelo de madurez de Richardson, checklist del contrato.
  2. u02_openapi.md — OpenAPI 3.1 y Swagger UI : anatomía del documento, descripción completa de /v1/books , componentes reutilizables, servir Swagger UI desde Express, una sola fuente de verdad generando el documento desde los schemas de Zod, generación del cliente tipado, tests de contrato con Ajv y detección de cambios incompatibles en CI.
  3. u02_graphql.md — GraphQL : over/under-fetching, esquema SDL (tipos, inputs, queries, mutations), resolvers sobre el mismo BookService , montaje en el Express existente, conexiones Relay vs page / pageSize , errores en extensions (y el "siempre 200"), N+1 y DataLoader, límites de profundidad y costo, comparación honesta REST vs GraphQL y cuándo elegir cada uno.

Hilo conductor: los tres extienden la API de libros de guia_tdd_api.md (en Moodle: Testing Parte 4 ), el mismo BookService y el mismo makeApp() . No se introduce un dominio nuevo: se le agregan capas. Ese mismo servicio es el que recibe autorización en la Unidad 3, persistencia real en la Unidad 4 y eventos en la Unidad 6.

Material previo que se apoya:

  • guia_tdd_api.md — la API de libros original, con Zod y Supertest
  • testing_api.md — estructura de una API Express para probarla

Estado: ✅ Cubierto. Los tres apuntes cubren los cinco temas del programa de la unidad. Queda pendiente generarlos como sección nueva en el aula virtual.

Posibles ampliaciones (no bloqueantes):

  • Colecciones Postman/Newman derivadas del documento OpenAPI (se solapa con la Unidad 8)
  • Federación de esquemas GraphQL (queda fuera del alcance de la materia)

UNIDAD 3: Autenticación y autorización

Temas del programa: OAuth 2.1/OIDC: authorization code, PKCE, scopes y claims. JWT: estructura, firmas, expiración y revocación. SSO y federación. Gestión de sesiones. Roles, permisos y control de acceso. Buenas prácticas de almacenamiento de credenciales.

Apuntes existentes en Prog4: ninguno.

Prerrequisito que se asume conocido (dictado en Programación III, no cuenta como cobertura y no se vuelve a dictar):

  • Prog3/clases/JWT.md — JWT en APIs con Express y TypeScript: estructura, firma, middlewares de autenticación, roles (1440 líneas, 34 secciones)
  • Prog3/proyecto/seguridad.md — JWT, CORS y CSRF integrados, implementación en React

Estado: 🔴 Sin cubrir. Es coherente con el aula virtual, que no tiene ninguna sección de autenticación: el JWT se dictó en Programación III. Lo que falta es exactamente lo que no se vio allá: el lado del protocolo delegado.

Falta escribir (asumiendo JWT conocido, sin repetirlo):

  • OAuth 2.1: flujo authorization code + PKCE, roles del protocolo, scopes
  • OpenID Connect: ID token, claims, diferencia con OAuth
  • Revocación de tokens y estrategia de refresh tokens
  • SSO y federación de identidad
  • Autorización como capa sobre la API de la Unidad 2: scopes → permisos → middleware
  • Almacenamiento de credenciales: hashing (argon2/bcrypt), secretos, dónde guardar tokens en el cliente

UNIDAD 4: Acceso a datos y persistencia

Temas del programa: Patrón repositorio. ORM (mapeo, migraciones, relaciones, transacciones). SQL vs NoSQL: selección y trade offs. Caché de lectura/escritura, invalidación. Integración con motores de búsqueda y colas de mensajes.

Apuntes existentes: ninguno en Prog4.

Material de otras materias (consulta o prerrequisito, no cobertura):

  • BdDII/sequalize/sequelize.md y example.md — ORM Sequelize: mapeo y relaciones
  • BDI/transacciones.md — transacciones
  • BdDII/neo4j_v2/ y BdDII/crud/crud_operations.md — NoSQL (grafos y documentos)
  • Prog3/orm/pymongo.md — MongoDB, aunque desde Python

⚠️ Decisión pendiente: qué ORM/estrategia usar para esta unidad. Sequelize ya se dictó en Programación III ( JWT.md ), así que repetirlo contradice el criterio de no re-dictar temas de Prog3. Alternativas: Prisma, Drizzle, o un repositorio a mano sobre pg para que el patrón quede explícito antes de taparlo con un ORM.

Estado: 🔴 Sin cubrir desde la perspectiva de Programación IV. Hay mucho material de bases de datos, pero nada sobre la capa de acceso a datos de una aplicación.

Falta escribir:

  • Patrón repositorio: motivación, interfaz, implementación en TypeScript, testeabilidad
  • ORM aplicado: migraciones versionadas, relaciones, transacciones y unit of work
  • SQL vs NoSQL: criterios de selección y trade-offs concretos
  • Caché de lectura/escritura (write-through, write-behind) e invalidación
  • Integración con motores de búsqueda y colas de mensajes

UNIDAD 5: Front End y consumo de APIs

Temas del programa: Consumo seguro (tokens, refresh, renovación). Gestión de estado (por ejemplo, context/store). Validación de formularios en cliente y servidor. Enrutamiento, protección de rutas y manejo de errores.

Apuntes existentes en Prog4 (sección "React con TypeScript" del aula):

  • react_ts.md — migración de React JS a TypeScript
  • React_peliculas.md — app completa con búsqueda, detalle y consumo de API (1292 líneas, 25 secciones)
  • React_TS_Gatos.md y React_TS_cat_simple.md — estados entrelazados, consumo de API
  • React_TS_Cat_bootstrap.md — la misma app con Bootstrap

Prerrequisito que se asume conocido (React de Programación III: hooks, useContext / useReducer , React Router, fetch vs axios , localStorage). No cuenta como cobertura.

Estado: 🟡 Parcial. Los apuntes de Prog4 enseñan React con TypeScript y consumo de API, pero los cuatro temas del programa de esta unidad (consumo seguro, gestión de estado, validación cliente/servidor, rutas protegidas) se apoyaban en el material de Prog3.

Falta escribir:

  • Consumo seguro: ciclo de refresh y renovación de tokens, interceptores, cola de reintentos (depende de la Unidad 3)
  • Gestión de estado a escala de aplicación, con TypeScript: store tipado, estado de servidor vs estado de UI
  • Validación de formularios con esquema compartido cliente/servidor (el mismo Zod de la Unidad 2)
  • Protección de rutas y manejo global de errores: error boundaries, mapeo de problem+json a mensajes de UI
  • Cliente generado desde OpenAPI ( openapi-fetch ) como alternativa a escribir fetch a mano — ya introducido en u02_openapi.md
